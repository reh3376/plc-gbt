AI Task Orchestrator - System Overview

Architecture, lifecycle, and interaction flows with annotated sequence indexes

Overview

The AI Task Orchestrator provides a contract-first, observable, and extensible framework for analyzing tasks, generating implementation guides, coordinating plugins, integrating memory systems, and validating outcomes. This page visualizes key flows and includes a sequence point index after each diagram to clarify what each numbered step represents.

Core principles: Async-first Plugin Hooks Observability Memory Integration Contract-First Two-Phase Testing

Purpose

This system turns high-level requests into reliable, production-grade outcomes. It guides AI agents through analysis → planning → implementation → validation → documentation, while enforcing strict API/schema governance and measurable quality gates across Python and TypeScript stacks.

Problems It Solves

  • Unstructured tasks and inconsistent delivery quality
  • Schema drift between frontend/backend
  • Ad-hoc error handling and missing observability
  • Insufficient validation and premature “done” states

Outcomes You Get

  • Contract-first APIs and type-safe integrations
  • Deterministic lifecycle with plugin extensibility
  • Two-phase testing: automated + user validation
  • Traceable deliverables with documentation by default

Architecture & Components

Core Modules

  • Orchestrator: lifecycle, context, coordination
  • Analyzer: task understanding, requirements
  • Validator: multi-tier checks (syntax → production)
  • Plugins: PRE/POST hooks and SHUTDOWN lifecycle
  • Observability: metrics, tracing, structured logs
  • Memory: Redis/Neo4j/PostgreSQL/Qdrant adapters

Contract-First Governance

  • OpenAPI Schema MCP as the single source of truth
  • Generated types only; no hand-written interfaces
  • Runtime validation on every request/response
  • Strict TypeScript rules (no any)

4) Complete Orchestrator Lifecycle

sequenceDiagram
  autonumber
  participant App
  participant Orc as AITaskOrchestrator
  participant MC as MetricsCollector
  participant Tr as Tracer
  participant PM as PluginManager
  participant Mem as Memory/Store

  App->>Orc: new AITaskOrchestrator(config)
  alt observability available
    Orc->>MC: get_metrics_collector()
    Orc->>Tr: get_tracer()
  end
  alt plugins available
    Orc->>PM: get_plugin_manager()
  end

  App->>Orc: __enter__() or __aenter__()
  alt plugins available
    Orc->>PM: startup()
  end
  Orc->>Mem: load context/memory
  Orc-->>App: self

  App->>Orc: execute_task_step(...)
  alt metrics/trace available
    Orc->>MC: record (with guard checks)
  end
  Orc->>Mem: read/write insights (robust shape handling)
  alt error
    Orc-->>App: raise ExecutionError(...) from e
  else success
    Orc-->>App: result
  end

  App->>Orc: __exit__() or __aexit__()
  alt plugins available
    Orc->>PM: shutdown()
  else no plugins
    note over Orc: no-op
  end
  Orc-->>App: closed (bool in async)

Governance & Testing (Non‑Negotiables)

Contract‑First (OpenAPI MCP)

  • Zero manual API types or UI schemas
  • Generate types from OpenAPI only
  • Runtime validation (request/response/UI)
  • Centralized error handling patterns

Two‑Phase Testing

  • Phase 1: Automated (Playwright MCP + unit/integration/a11y/perf)
  • Phase 2: User interactive testing (mandatory)
  • No feature marked complete until both phases pass

Quick Starts

Python (60s)

from plc_gbt_stack.ai import AITaskOrchestrator

with AITaskOrchestrator() as orchestrator:
    analysis = orchestrator.analyze_task("Create PLC data parser")
    guide = orchestrator.create_implementation_guide(analysis)
    print(guide)

TypeScript/Next.js

import { createOrchestrator } from '@plc-gbt/orchestrator'

const orchestrator = createOrchestrator()
const analysis = await orchestrator.analyzeTask('Create React data table component')
const validation = await orchestrator.validateImplementation(code)

AI Coding Agent Base Prompts

Frontend Prompt


1. Review the latest UI architecture, design system, and accessibility requirements documented in `@ui/docs/architecture/THEIA_ARCHITECTURE_SPECIFICATION.md` 
and related guides before making any interface changes.

2. Reference @AI_TASK_ORCHESTRATOR_TS_GUIDE.md together with @ai_task_orchestrator_ts.ts whenever orchestration behavior, task sequencing, 
or automation hooks affect the feature. Review these resources early in planning and again before finalizing work that touches orchestrator flows 
to ensure alignment with the TypeScript implementation details.

3. Collect active context before coding. Read the user request, inspect relevant files, and capture current UI state or API contracts so the 
hypothesis about required changes is grounded in actual project data.

4. Consult @DEVELOPMENT_GUIDE.md after the initial scan. Use it to confirm architecture expectations, naming conventions, and any in-progress 
initiatives that should influence the solution before drafting implementation notes.

5. Coordinate implementation with Theia extension guidelines and shared components to keep the shell, panels, and workflows consistent across the IDE.

6. Decide whether you are prototyping or delivering production-ready UI work, documenting exploratory branches clearly and polishing production 
code to meet linting and UX quality bars.

7. Run the mandated UI test suites (Playwright, linting, and visual regression checks) and resolve failures before requesting review.

8. Once automnated and user interactive testing comfirms task(s) are complete Apply the planned changes, keep commits focused, run all mandatory 
frontend and backend tests (including linting, type checks, and unit suites), and summarize results before handing off the task. Assigned task(s) follow:

Backend Prompt


1. Review `@DEVELOPMENT_GUIDE.md`, `@plc_memory_system_overview.md`, and `plc-gbt-stack/DOCKER_ENVIRONMENT_STATUS.md` to ground yourself in the 
PLC Memory architecture (Redis, Neo4j, PostgreSQL, Qdrant), confirm the Docker MCP server on `http://localhost:8811`, and note the CLI entry point 
at `plc-gbt-stack/scripts/ai/plc_memory_cli.py` before planning work.

2. Drive every assignment through the methodology in `plc-gbt-stack/docs/AI_TASK_ORCHESTRATOR_GUIDE.md`, using `plc-gbt-stack/ai/ai_task_orchestrator.py` 
to analyze requirements, enumerate dependencies (databases, MCP schemas, workflow nodes), and script the implementation stages.

3. Decide early whether you are prototyping or shipping production code; spikes must explicitly document limitations, while production changes must 
integrate with the PLC Memory flows (ingest, query, backup, monitoring) and uphold repository standards.

4. Take advantage of the MCP-powered tooling—plc memory, code optimizer, fine-tuned SME LLM, and other exposed services—available through the locally 
running Socket MCP Docker environment when planning and executing your work.

5. Run the required validation for the scope you touch—`pytest`/`ruff` suites, orchestrator or CLI smoke commands (e.g., `python plc-gbt-stack/scripts/ai/plc_memory_cli.py status`)
, and Docker MCP connectivity checks—and resolve every failure before requesting review.
